# 储物柜 SaaS · 业务规划（阶段 1 起）

> 领域于 2026-10-08 由"换电柜"切换为"储物柜"（城市、多点位、多柜机的临时寄存）。
> 本文取代已废弃的《阶段1换电业务规划》。约定的唯一来源仍是 [`架构约定.md`](./架构约定.md)；
> 本文只记**方向、决策、验收口径**，不记实现细节。
> **元规则**：每刀开工前必须按 §14 的四问重新详细思考那一刀——上一刀的实际编码结果很可能打乱本刀的原设想。

---

## 1. 定位与规模（数字要能撑起深度）

一个运营商在**一座城市**运营寄存网络：点位（商场/车站/景区）→ 柜机 → 格口。

- 点位 **60**，每点位 1~4 台，共 **180 台柜机**
- 柜机模板 **6 大 + 8 中 + 10 小 = 24 格口**，合计约 **4320 个格口**
- 寄存客户 **10 万级**；日均寄存单 **3 万**（节假日峰值 5 万）→ 年订单 **约 1000 万行**
- 常态消息量很小（心跳 6 msg/s），但**故障时是风暴**：一台柜机重连补报数十条、批量掉线瞬时数百连接
- 热点在**单台柜机的大格口**：同一时刻十几人抢 2 个大格口是常态场景

选这个量级的理由不是"像真实系统"，而是**只有这个量级，下面这些才成为真问题**：单表千万行的索引与冷热分层、归档与只读历史、热点争抢的锁粒度、上报风暴的背压、对账批处理的分片。数据量小的项目里这些只能背八股。

代价与对策：种子数据必须**脚本生成**（`scripts/seed-locker.mjs`，含真实分布：点位数、时段分布、故障柜占比）；设备模拟器**一进程带多柜机**（180 个 clientId 用线程/事件循环，不启 180 个进程）。

## 2. 已定决策

- **S-01 支付形态**：点数储值（虚拟货币，1 点 = 1 分人民币口径），充值获得、消费扣减。对外表述："预付储值账户 + 可插拔支付通道"，不说"虚拟货币"。
- **S-02 记账走轻档**：单一 `points` 余额 + **押金独立一栏**（点数会被消耗，押金必须可退，义务不同故不混列）；流水只 INSERT、余额为派生值。**不做**双分录、本金/赠送分离、退款比例折算、对账四分类。留升级口子：流水带业务类型与关联单号，账户允许再加余额列。
- **S-03 押金**：**每单固定点数**（按尺寸可配固定值），存件时收、订单关闭后独立退还。
- **S-04 转柜（跨柜挪件）不做**：会把一张单变成两张单的迁移问题，复杂度花在业务形态而非技术深度。
- **S-05 身份**：不依赖微信授权。`CustomerIdentityResolver` 三实现：H5 匿名/稳定标识（现在）、mock code（已有通道复用）、微信 openid（将来换适配器）。扫码的本质是**把带柜机编号的深链交到用户手里**。
- **S-06 价格**：价格是**计费策略的输出**，不是格口属性；策略可随点位/尺寸/时长阶梯不同；**下单时把策略与计算明细快照进订单**（改价不污染历史，投诉可重算）。
- **S-07 时间权威**：计费与状态推进一律以**服务端时间**为准，设备时钟仅作参考（防柜机时间错乱导致大面积错收）。
- **S-08 设备定位**：虚拟设备**不是重点**，唯一职责是**可控的故障注入源**（每类故障可按柜机开关）。不做门磁以外的传感器、不做固件 OTA、不做设备影子、不做遥测曲线。
- **S-09 降级方向**：柜机离线时**不可存、可取**；错误处理整体偏向"放人"而非"卡人"。
- **S-10 营销**：优惠券/满减/会员等级/拼团全部不做。仅保留"免费取消窗口"与"续期"两个真实动作。
- **S-11 支付通道**：`PayChannel` 抽象保留，实现先用 Mock；真实支付宝/微信推到项目最后（用户不倾向做，且受资质与公网回调限制）。
- **S-12 不做 MySQL 分区**（用户授权助手定）：订单表**主键不含日期**，改用 `created_at` 冗余列 + **归档历史表**（`biz_storage_order_archive`）做冷热分层。理由：分区要求分区键进入每个唯一键（与雪花主键相冲），对 MyBatis-Plus 与 Flyway 迁移都添麻烦，收益主要在有专职 DBA 的运维侧；归档表方案能同样支撑“单表不无限增长”并能用测试验证。
- **S-13 身份表改名**：`sys_rider` 与寄存客户列几乎一一对应，**用 `RENAME TABLE` 元数据操作转为 `biz_customer`**（瞬时、不复制行、索引保留），Java 侧 `SysRider`→`BizCustomer`、`RiderAuthService`→`CustomerAuthService`、`/api/mini/auth/*` 契约不变但响应改 `CustomerView`；mini 前端同步字段。**必须与第 8 刀同期完成**，否则寄存单会外键指向一张换电语义的表。
- **S-14 柜机型号模板进租户白名单**：硬件型号（6大/8中/10小 的组合）是平台维护的字典，租户只引用，不带 `tenant_id`。
- **S-15 点数账户与流水表在第 8 刀建结构**，资金逻辑留第 12 刀：避免后期回改订单表字段（否则“冻结额”这种列要补数据）。

## 3. 对象与关系

点位 1:N 柜机；柜机 N:1 柜机型号模板（模板决定 6/8/10 的组合，**建柜机时按模板生成格口，禁止人工逐门录入**）；柜机 1:N 格口。

一张**寄存单**关联：客户 + 点位 + 柜机 + 格口 + 尺寸 + 价格策略快照与计算明细 + 取件凭证（短码，可多条，重发即新增并作废旧的）+ 冻结点数记录 + 押金记录 + 状态机 + 乐观锁版本。

设备侧两张**只增流水**：`指令流水`（requestId、目标柜机/格口、下发时间、回执状态、重试次数）与`上报流水`（事件类型、seq、设备时间、入库时间）；两者都回连寄存单，用途是重放、对账、定位。

另有：格口/柜机的**故障事件流水**（连续失败计数、停用与恢复、操作人），`延迟任务表`（超时未关、超时未取、押金退款重试、对账批次共用一套设施）。

## 4. 不变量（必须写成测试，是全部说服力的来源）

1. 同一格口在同一时刻**至多一个活动寄存单**（并发分配后校验，超卖数恒为 0）。
2. 格口状态与订单存在性一致：`占用 ⇒ 存在活动单`，`空闲 ⇒ 不存在`（不允许"占用但空"或"有单但空闲"）。
3. 资金：`points >= 0`、`Σ(点数流水) == 余额`、`冻结总额 == 未结算订单应冻额之和`。
4. 押金不悬挂：每笔押金属"未收/已收待退/退款中/已退/退款失败待人工"之一，且"订单已关闭且超过 N 天但未退"的集合必须为空（非空即告警）。
5. 柜机离线期间不存在**新分配**（可有存量单）。
6. **活动单不得被逻辑删除**：`deleted=1` 不会把 `active_flag` 置 NULL，唯一索引仍占位，
   格口会永久不可用。作废/归档必须先转终态再删（已写入 `架构约定.md` §3.5）。

## 5. 用户操作流程（含每步的防护）

1. 扫码/输编号进入点位页：看各尺寸可用数（Redis 计数，DB 为准定时校准）。
2. 选尺寸 → **预占格口**（短 TTL 3 分钟；同一客户重复点击复用同一预占；到期自动释放）。
3. 确认投件 → 收押金 + **按预估时长冻结点数**（点数不足直接拒，不允许先开柜后算账）。
4. 下发开柜指令 → 柜机开门 → **收到"已开门"回执前不推进状态**（不猜成功）。
5. 客户放件、关门 → 门磁"已关"上报 → 订单转 `ACTIVE` 并开始计费。
6. **超时未关门 → 自动撤销**：解冻点数、释放格口、退押金发起、提示重投（最高频真实事故）。
7. 期间**临时开柜**：中间态 `TEMP_OPEN`，此刻格口不可回收/不可再分配/不可重复开门；免费 N 次，超出计费；开后超时未关 → 告警并标故障。
8. 续期：再冻结一次，**沿用原策略快照**（同一单不中途换价）。
9. 取件：输码 → **结算**（按实际时长核销，差额解冻或补扣）→ 开门 → 取件关门 → 订单 `CLOSED`；**押金退还在关闭后独立异步发起**。
10. 超时未取：阶梯计费至封顶 → 提醒 → 转滞留工单；**欠费仍可取件**（欠的是债，不是留置权），只限制下次使用。
11. 反复输错取件码：锁定该单的开柜能力，但保留**备用路径**（客服核验 → 后台强制开柜 + 审计）。

## 6. 业务管理员（运营后台）

角色：客服（查单、补发取件码、申请开柜）｜运维（格口与柜机停用/恢复、故障工单）｜财务（点数流水、未退押金清单、对账差异）｜超管（点位与柜机、价格策略发布、权限）。

能力按"看得清 / 改得动 / 留痕迹"组织：格口占用与故障视图；异常与工单队列（**每个异常都要有"待人工"出口，禁止静默失败**）；设备健康看板（连续失败计数、离线清单）；价格策略版本化发布 + **按点位灰度**；订单与资金流水查询（沿用分页契约与权限码）；未退押金清单；对账漂移修复提案（人工确认才执行，不自动改库）。

高危动作约束：**强制开柜**必须二次确认 + 审计（谁/何时/哪单/理由）+ 配额（每人每日 N 次）+ 超限告警。绕开业务规则的每一个口子都要能被统计，否则后门会常态化。

## 7. 防呆清单

1) 尺寸不符不硬塞：提示换格口并**释放已分配格口**；2) **免费取消窗口**（5 分钟内全额退）；3) 关门确认前不计费不扣点；4) 重复点击与弱网重试全幂等（requestId + 业务键双层，重放返回首次结果）；5) 取件码锁定但永远留备用开柜路径；6) 欠费可取件；7) 预占有 TTL、中间态各有"最迟完成时间"；8) 格口标故障后不再被分配，**存量单不受影响**；9) 计费只用服务端时间；10) 价格策略下单快照；11) 柜机按模板生成格口；12) 押金退失败自动重试 + 超期未退清单，绝不静默吞掉。

## 8. 突发错误与应对（失败模式 → 检测 → 自动动作 → 人工出口 → 如何测）

1. 指令无回执 → 超时转"待确认"，幂等重试；仍失败则回退且不动资金；测试注入"永不回执"。
2. 谎报"已关门" → 门磁二次校验/超时未闭合 → 撤销寄存 + 解冻 + 格口标故障 + 工单。
3. 部分成功（该开两门只开一门）→ 整体判失败，回滚已开侧并重新分配。
4. 重复/乱序上报 → 按 seq 单调收敛，禁止旧事件让状态倒退；重复命中幂等表丢弃并计数。
5. 柜机离线 → 标离线、拒绝新分配、**仍允许取件**；恢复后积压上报经有界队列 + 丢弃策略 + 告警消化。
6. 格口硬件坏 → 连续失败计数达阈值摘出可分配池 + 告警 + 恢复流程。
7. 消费失败/堆积 → 指数退避 → 死信 → 工单；消费幂等；堆积深度进指标告警。
8. 结算补扣失败 → 欠费台账 + 不阻断取件 + 限制下次 + 催收任务。
9. 并发扣成负余额 → 条件 UPDATE 是唯一防线，压测断言余额恒 ≥ 0。
10. 对账漂移（Σ流水 ≠ 余额）→ 校准任务发现 → 生成修复提案 → 人工确认执行。

## 9. Redis / MQ 的使用边界

Redis 用在哪：格口可用数计数（DB 为准 + 定时校准）、预占与分配的短 TTL 锁与幂等键（Lua 原子）、限流（固定窗口升级为滑动窗口）、延迟队列 ZSet（与 MQ 定时消息做同需求双实现）、设备在线状态（心跳键 TTL + 遗嘱双保险）、登录态与黑名单（已有）。
Redis **不用**在：点数余额的真相、订单主数据、跨服务事务。**钱以 MySQL 流水为准。**

RocketMQ 用在哪：设备上报削峰、订单状态事件驱动下游（结算/缓存失效/统计，可重放）、**本地消息表或事务消息**保证"扣点"与"发事件"不错配、定时与延迟消息承载四类超时。
MQ **不用**在：开柜指令的下发通道——下发要低延迟与明确成败，MQ 只增加不确定层；但**回执的上行必须走队列**。（这是要能讲清的取舍。）

## 10. Java 技术深度（五件主打，其余照 §1~§9 自然生长）

1. **格口争抢的四种并发控制**：`FOR UPDATE`（含间隙锁范围问题）/ 条件 UPDATE CAS / Redis+Lua 预扣 / Redisson 分柜机锁；JMeter 100/500/1000 对照报告（吞吐、P99、重试率、**超卖=0**）；外加"持锁期间进程被 kill"的混沌测试。
2. **状态机 + 补偿**：合法迁移矩阵（单测穷举非法迁移被拒）、中间态超时收敛、Saga（冻结→开柜→核销，每环有补偿，**补偿也失败进悬挂 + 工单**）。
3. **统一延迟任务与调度**：一张任务表 + 处理器注册，后端可插拔（MQ 定时 / ZSet / 扫表抢占）；多实例互斥三方案对比（锁选主 / 抢占 SQL / 分片）及各自失效场景。
4. **资金一致性**：条件 UPDATE 防超扣、只增流水、余额可重算、三段式冻结-核销-补扣、押金独立义务与未退清单、幂等入账、金额整型分/点 + BigDecimal 运算。
5. **可验证性**：故障注入器 + **不变量混沌测试**（§4 在随机注入故障下仍成立）+ traceId 贯穿 HTTP→MQ→指令→回执→结算 + 指标与 GC 证据。
6. **数据库层**：索引与 B+ 树不是背景知识，而是 §16 里的**结构约束**——尤其“用唯一索引在数据库层防住超卖”，这不靠应用逻辑自觉。

## 11. 中间件选型（三档，含理由）

**建议真用**：Nginx（反代/TLS/静态/限流兜底）｜Caffeine 本地缓存构成**二级缓存**（本地 + Redis + 失效广播，正好治"格口计数"这个热点）｜Micrometer Tracing + Zipkin/Tempo（把 traceId 变可视链路，含 MQ 跨线程传播）｜Prometheus + Grafana + Alertmanager + node_exporter，日志用 **Loki**（轻量，替代 ELK）｜Arthas（线上诊断，零常驻成本）｜Redisson（锁方案之一）。
**可选（有明确代价）**：XXL-JOB 或 PowerJob（调度中心，多一进程+一库；**默认自己实现分片抢占**，若要做对照再引）｜Canal/Debezium（binlog 驱动缓存失效与统计异构，成本一进程）｜MinIO（对账/导出文件，先用本地目录）｜Sentinel（若只为简历关键词，可只演示规则；**自研熔断状态机更值钱**）。
**不引入，并说清为什么**：Elasticsearch（无真实全文需求、内存吃不下；搜索走 MySQL 索引 + 归档）｜Seata（主张是最终一致 + Saga/本地消息表，与强一致分布式事务冲突）｜Nacos/Apollo（单服务，配置在 DB + 版本快照 + 事件刷新即可）｜Spring Cloud Gateway、注册中心、微服务拆分（规模不需要，拆分是复杂度不是深度）｜Kafka（RocketMQ 已覆盖）｜ShardingSphere（**先手写分表路由与归档**，懂原理再引框架）。

## 12. 运维

部署：systemd（JVM 参数复用 `deploy/jvm.opts` 单一来源）+ Nginx + HTTPS；云上常驻只加 **Nginx + broker + node_exporter**（约 400MB，服务器可用约 2.9G），Prometheus/Grafana 我本地跑或按次起。
可靠性：`mysqldump` 备份 + 落地远端 + **真做一次恢复演练**；Flyway 两阶段变更（先加后删，禁破坏性迁移）；健康检查失败自动回滚；**按点位灰度**。
可观测：埋点（已有）→ 抓取；看板看堆/GC/HikariCP 连接池/MQ 堆积深度/分配失败率/P99；结构化日志 + traceId + 慢 SQL。
拨测告警：GitHub Actions cron 打健康检查与关键接口 + 证书与磁盘到期 → webhook 通知（有真实在线对象后再做）。
安全：安全组只开 22/80/443/8883；3306/6379 不对公网；MQTT 必须 TLS + 认证 + **ACL（每台柜机只能读写自己的 topic）**；密钥只进 `.env`。
交付物：**runbook**——柜机批量离线、MQ 堆积、超卖告警、对账漂移各一份处置步骤。

## 16. 数据库与索引专项（B+ 树、索引、join 在这里真的会用到）

### 16.1 主键与聚簇索引
主键用雪花 ID（`assign_id`，底座已定）而不是 UUID：B+ 树叶子层按键有序，**趋势递增→页分裂少、页填充率高、二级索引不会跟着膨胀**；随机主键会把写变成随机 IO 并留下大量碎片。能顺带讲清“为什么二级索引叶子存的是主键而不是行地址”（页分裂时不必重建二级索引）。

### 16.2 仍由数据库兑现的约束（最重要的一条）
- **结构性防超卖**：`UNIQUE (slot_id, active_flag)`，`active_flag` 活动期写 1、订单结束置 `NULL`。MySQL 唯一索引**允许多个 NULL**，所以同一格口只能存在一条活动单、历史单无限多——**超卖在存储层就做不到，而不是靠应用代码严谨慎**。这是本项目最硬的一个索引设计。
- 格口分配：`idx_slot_acquire (cabinet_id, size_type, status)`。为什么这个顺序：`cabinet_id` 先把范围缩到 24 行，`status` 单列区分度只有 5 个值、**单独建索引毫无意义**（优化器也不会用）。
- 取件码：`uk_code (code)` 全局唯一且**不可枚举**（随机码，不用自增短码），同时防碰撞重试。
- 订单列表：`idx_order_tenant_time (tenant_id, created_at)`；调度扫描：`idx_order_scan (status, finish_deadline)`（**满足最左前缀**，否则优化器不用它）。
- 流水：`idx_cmd_request_id`（回执幂等定位）、`idx_report_cabinet_seq (cabinet_id, seq)`（乱序收敛与重放）。
- 点数流水：`uk_biz (biz_type, biz_no)` 保证**同一业务事件只能入账一次**（幂等下沉到索引层）。

### 16.3 覆盖索引、回表与“不要堆宽索引”
只取索引已有列时 `Using index`（免回表）；需宽字段时**不要为了省回表把索引做成七八列**——写放大、页占用、缓冲池命中率下降都是真代价。判断标准写进约定：**高频读 + 列小 + 不回表收益明确**才做覆盖索引（典型：首页的“各尺寸可用数”统计）。

### 16.4 索引失效清单（做成测试，不只写在文档里）
函数包裹索引列（`DATE(created_at)=?` → 改区间）、**隐式类型转换**（varchar 列传数字）、前导 `%` 的 LIKE、`OR` 混入非索引列、不满足最左前缀、join 两侧字符集/排序规则不一致。→ 每个失效例子配一条断言行数或 `key` 的 EXPLAIN 回归测试。

### 16.5 深分页与 count
`LIMIT 1000000,20` 的代价是**B+ 树顺序扫过一百万条再丢弃**；后台历史查询用**游标式（seek）**：`WHERE id < ? ORDER BY id DESC LIMIT 20`。现有契约上再加两道：`pageSize<=200`（已有）+ 页码上限，超限时返回明确错误而不是默默变慢；大列表的精确 `count(*)` 改成估算/可关闭（否则分页本身就是性能陷阱）。注意一对多 join 时分页与 count 会错（重复行使 total 偏大）。

### 16.6 间隙锁与 next-key lock（“锁为什么会卡住不相干的插入”）
`SELECT ... FOR UPDATE` 走二级索引时，InnoDB 不只锁命中行，**还锁住索引记录之间的间隙**，其他事务往该范围 INSERT 会被阻塞——这就是“分配并发下莫名变慢”的真因。对策与实验：用条件 UPDATE 一步定位并修改（避免先查后改的窗口）、主键/唯一索引定位单行、必要时 `FOR UPDATE SKIP LOCKED`（**延迟任务表多实例抢占的天然工具**：一个实例取走的行对其他实例不可见，不重复执行也不互相阻塞）与 `NOWAIT` 快速失败；锁范围与阻塞关系用 `performance_schema.data_locks` + `information_schema.innodb_trx` 实测取证据，而不是背结论。

### 16.7 Join 的取舍（写成规则，避免“能 join 就 join”）
默认**不写 join**：单表查询 + 应用层组装（兼容租户插件、归档与未来分片；跨表 join 在归档后会坏）。**快照优先于 join**：点位名、尺寸名、价格策略与计算明细全部快照进订单（反正 S-06 要求快照）。允许 join 的两类：后台只读多表列表、报表聚合；且**必须附 EXPLAIN 结果**进代码注释或测试。另加一个 **N+1 检测拦截器**：单请求 SQL 条数超阈值就告警（嵌套 `<select>` 造成的 N+1 是这类项目最隐蔽的性能坑）。能讲的原理：MySQL 8.0.18+ 的 **hash join** 什么条件下启用、为什么小结果集还是 nested loop 更优。

### 16.8 数据生命周期与在线变更
单表千万行后的安排：按 S-12 **不做 MySQL 分区**，而是 `created_at` 冗余列 + 归档历史表（`biz_storage_order_archive`）；归档作业按“已结束且满 N 天”分批迁移，冷热查询入口分开（列表默认只打热表，历史入口显式标“查历史”并走归档表，两表结果合并时归档表仅追加）；在线加索引用 `ALGORITHM=INPLACE, LOCK=NONE` 并知道大表耗时与主从延迟；Flyway 一律两阶段变更（先加后删，**禁止破坏性迁移**）。归档的可用性与完整性靠“归档后热表行数 + 冷表行数 == 归档前行数”的断言守护。

### 16.9 连接与诊断
HikariCP 池大小要与 MySQL `max_connections` 匹配，“池越大越好”是错的（长事务 + join 大结果集会同时占住连接与内存）；故障时查 `innodb_trx` 找长事务、`data_locks` 找锁等待、`performance_schema.events_statements_summary_by_digest` 找昂贵 SQL；慢查询日志 `long_query_time` 设到 200ms；应用侧用 Arthas 抓锁等待与 GC 停顿。

### 16.10 PostgreSQL（只给阶段 3 的 agent 用）
向量索引 HNSW/IVFFlat 的选型与召回权衡；**不做跨库 join**（MySQL 与 PG 间只通过异步同步或应用层组装，否则一致性无法保证）。
