# 延迟任务三种触发方式：同一需求三实现与实测对比

> 第 13 刀产物。代码在 `server/src/main/java/com/wherelee/cabinet/infrastructure/task/`
> （`PollTrigger` / `ZsetTrigger` / `MqTrigger`）与 `application/task/`（任务表、处理器、worker）。
> 数字来自本文 §4 那四条命令的真实运行，不是推想。

---

## 1. 一句话结论

**三种触发方式都不持有执行权，执行权只在 `biz_delay_task` 上的一次条件更新。**

所以它们不是"三选一"，而是**同一张表上的三个提醒源**：谁响了都要去 DB 抢，抢不到就不执行。
这件事决定了后面所有结论——也是我先写测试再写实现的原因（§3 的并发用例在实现之前就知道要证什么）。

## 2. 三者的分工

| | 触发时机 | 依赖 | 到期精度 | 提醒能否丢 | 谁来保底 |
|---|---|---|---|---|---|
| `poll`（默认） | 每 `poll-interval-ms` 扫一次到期行 | 只有 DB | 由间隔决定（下限=0，上限=一个间隔） | 无所谓（**没有独立提醒**，扫表本身就是执行） | 它就是保底 |
| `zset` | 注册时 `ZADD`，drain 循环取到期成员 → 触发一轮抢占 | Redis | drain 间隔（本项目 200ms~1s） | **能丢**（写完 DB 崩在 ZADD 前、取出后崩溃） | 类内自带一条慢轮询 |
| `mq` | 注册时发延迟消息，消费者收到 → 触发一轮抢占 | RocketMQ | **只有 18 个固定档位**（§5） | 能丢（broker 抖动、发送失败） | 同样有慢轮询兜底 |

三者可以同时开：提醒多打几次不改变正确性（租约条件更新只允许一个人拿到 1 行），
提醒一次没打也不影响正确性，只影响延迟。

## 3. 为什么"提醒可以随便重、随便丢"能成立

三条不变式，全部有测试钉住（`DelayTaskTest`、`SchedulerBackgroundPollTest`）：

1. **登记幂等**：`uk_task_type_key (task_type, biz_key)` + `ON DUPLICATE` 规则——
   `PENDING/FAILED` 只把 `fire_at` **提前**（`least`），`RUNNING` 不动，`DONE` 视为新一轮起点直接取新值，
   `DEAD` 永不静默复活。重复登记一百次也只有一行，且不会把到期时间推后。
2. **执行权 = 一次条件更新**：`claim` 的 `WHERE` 重复了"可抢"判据，影响 1 行才算拿到；
   `markDone` 带 `lease_owner`，丢了租约就抛异常回滚业务（**不允许"业务做完但状态没落"**）。
3. **失败记录另起事务**：退避时间与 `attempt` 若和业务共用事务，回滚会把它们一起抹掉，
   指数退避形同不存在，坏数据会以轮询频率打爆日志。

并发用例的断言不是"跑完没报错"，而是**每个 bizKey 的 `attempt` 恰为 1**、执行总数恰等于任务数——
`attempt` 是"被抢了几次"的硬证据，双执行一定会让它 >1。

## 4. 实测延迟（同一台机器、同一库、同一批代码）

| 模式 | 配置 | 样本 | 实测 `到期→执行完成` 延迟 |
|---|---|---|---|
| poll | `poll-interval-ms=500` | 1 个真实超时释放 | **1735 ms** |
| zset | `zset-interval-ms=200` + 兜底轮询 1000 ms | 5 个任务 | max **156 ms**，avg 68 ms |
| zset（提醒被抹掉） | 同上 | 3 个任务 | max **244 ms**（落在兜底轮询的哪个位置决定，见下） |
| mq | 延迟档位 2（5s） | 1 个任务 | **206 ms**（`attempt=1`） |

复现命令：

```powershell
mvn -B -ntp test -Pintegration "-Dtest=SchedulerZsetTriggerTest,SchedulerMqTriggerTest,SchedulerBackgroundPollTest"
```

四条读数怎么解释：

- **poll 的 1735 ms 不等于"间隔 500ms"**。这一段包含：等下一次轮询启动 + 抢批 + 执行 handler
  （真实业务：取消订单、解冻点数、释放格口）+ 落 `update_time`。所以"轮询延迟=一个间隔"是纸面推导，
  **端到端要按 3~4 个间隔估**。这也是我不把断言写成"2 倍间隔"的原因——那会是个飘红的用例。
- **zset 的 156 ms 是它的价值**：不用扫表也能在亚秒级响应，代价是多一个 Redis 依赖。
- **"提醒被抹掉"那一行值得单独说**：结果仍然正确（任务被执行），延迟退化成兜底轮询的粒度。
  这一次实测恰好 244 ms（落在轮询周期前段），换一次运行可能是 900 ms——
  **数字不稳是设计内的**，用例断言的是"必须被执行完"，不是"必须多快"。
- **mq 的 206 ms** 说明 broker 投递本身很准；**问题不在抖动，在粒度**（§5）。

## 5. MQ 的真实约束：18 个档位，不是任意时刻

`rocketmq-spring 2.3.1` 的 `syncSend(dest, msg, timeout, delayLevel)` 只接受档位号
（1s 5s 10s 30s 1m 2m 3m … 10m 20m 30m 1h 2h）。要任意时刻需要 5.x 的 `TIMER_DELIVER_MS` 头。

于是"精度"变成一个**量化误差**问题。全表扫描（`MqDelayLevelTest`）的结论：

| 目标延迟 | 实际得到 | 过冲 |
|---|---|---|
| 1.001 s | 5 s | 4 s |
| 31 s | 60 s | 29 s |
| 1001 s（≈16.7m） | 1200 s | 199 s |
| 3601 s（1h+1s） | 7200 s | **3599 s** |

**取整方向必须是向上**，这不是风格而是安全：提前触发等于把还在用的格口判成超时（误释放），
晚几秒只是用户多等一下。两个方向的代价不对称，所以取整方向也不能对称。
这条已经写进测试（`roundingDirectionIsAsymmetric`），防止日后有人"为了精度"改成 `Math.round`。

## 6. 多实例：三种抢占方案与各自失效场景

| 方案 | 怎么做 | 会坏在哪 | 本项目 |
|---|---|---|---|
| 锁选主（Redis/ZK） | 只有 leader 扫描执行 | 选主与执行是两个时刻：leader 拿到任务后网络分区，别的实例接管，**旧 leader 还在跑** → 双执行。要正确就得把租约贯穿执行全程 | 不用：等于把 `biz_delay_task` 的租约搬到 Redis，而 Redis 上没有事务 |
| 抢占 SQL | `FOR UPDATE SKIP LOCKED` 取候选 + 条件更新抢租约 | 单库瓶颈（但每轮只锁一批，不排队）；MySQL 8 才支持 `SKIP LOCKED` | **采用**，见 §7 |
| 分片（instanceIndex） | 每个实例按 `id % N` 取自己的分片 | N 变了（扩缩容/重启时序不一致）会**双执行或漏执行**，且没有任何报错 | 不用：180 台柜机的量级不需要横向扩到几十实例 |

关键的一点：**"谁执行"必须与"什么时候提醒"解耦**。否则换触发方式就要换并发方案，两件事互相污染。

## 7. 抢占为什么写成"两条语句"而不是"一条 update 顶到底"

```sql
select id from biz_delay_task
 where deleted = 0
   and ((status in ('PENDING','FAILED') and fire_at <= now(3))
     or (status = 'RUNNING' and lease_expire_at < now(3)))
 order by fire_at limit ? for update skip locked;   -- ① 候选集，互不相交、不排队
update biz_delay_task set status='RUNNING', lease_owner=?, lease_expire_at=?, attempt=attempt+1
 where id = ? and deleted = 0 and (同上判据);        -- ② 真正的所有权判决
```

- ① 只解决"别看同一批行"，**不解决归属**；② 才是裁判。合起来才既有吞吐又不重复。
- 判据里带 `FAILED`：失败退避后的状态就是 FAILED，只认 PENDING 会让重试**永远跑不到且不报错**
  （本刀实测到过，症状是"任务躺在库里到地老天荒"）。
- `RUNNING and lease_expire_at < now`：没有这一条，实例被 kill 会让任务永久卡在 RUNNING。
- 单测里两个并发事务的候选集**必须不相交**（`skipLockedGivesDisjointCandidates`）。
  不断言"各拿几条"——那由扫描与加锁交错决定，不是 SKIP LOCKED 的承诺（实测一个拿 4、一个拿 1，
  因为 next-key 锁的区间比返回行大）。

## 8. 已知边界（写出来而不是藏着）

1. **调度线程没有租户上下文**：worker 取任务行必须走 `@InterceptorIgnore` 的专用查询，
   用 `BaseMapper.selectById` 会被"无上下文即拒绝"的守卫卡住——症状是**后台轮询一个任务也不执行**。
   这条是靠"不关掉 poll 的那条用例"暴露的（其余调度用例都关 poll 手工驱动，全绿也照样漏）。
2. **`fire_at` 与 `now(3)` 不同源**：Java 侧算的到期时刻与 MySQL 时钟比。同机部署误差在毫秒级；
   **跨网部署时这 2 秒的差就会决定"提前触发"**——所以 MQ 模式一律向上取整，且 broker 上云后要重估
   （第 16 刀）。
3. **租约时长必须显著大于单任务耗时**，否则任务还在跑就被接管，变成双执行；
   本项目默认 60s，`convergeDeviceOutcome` 这类要等回执的 handler 已改为不持有外层事务（§9）。
4. **对账只报告不改钱**（`ReconcileService` 的三条立身之本之一）：自动"修平"账本会把 bug 埋进账本；
   差异进 Gauge/日志/`biz_delay_task` 的重试登记，动钱必须留人工痕迹。
5. **滞留单**：封顶到达或盯满 `stranded-days` 就停止续排并 `log.error` + 计数，
   **后台工单队列在第 14 刀**——本刀只保证"永远数得出来"，不保证"有人被派工"。

## 9. 一个反直觉的收获（写下来免得下次重踩）

`TransactionTemplate` 在 `@Transactional` 方法内部调用**不会新开事务**（默认 `REQUIRED`），
所以"等回执不持事务"的拆法会被外层重新合上。调度 worker 原本无条件把 handler 包进事务，
这让 `CommandRescanHandler`（内部要等 2.5 秒设备回执）在**每次回扫时都占着一个连接**——
正是第 9 刀压测量出来的瓶颈形态。

结论：`TaskHandler` 必须有"我需不需要事务"这个自述位（`transactional()`），
默认 true（业务与 `markDone` 原子，防半现场），**要等外部 I/O 的 handler 显式标 false 并承担完全可重入的义务**。
