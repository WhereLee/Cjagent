# 压测报告 · 格口分配（第 9 刀）

> 日期 2026-10-09，机器：本机 Windows + 本地 MySQL 8.0.44（开发库 `cabinet_dev`），
> 被测：`cabinet-server` 单实例（`mvn spring-boot:run`，JDK 17），
> 工具：JMeter 5.6.3（脚本 `stress/slot-allocation.jmx`，跑批 `stress/run-round.ps1`）。
> 复现：`powershell -File stress/run-round.ps1 -Threads 500 -Tag cas`，
> 需要 `stress/results/load.properties`（`token/cabinet/size`，token 由 `/api/mini/auth/login` 取，不入库）。

## 1. 测的是什么

单个热点柜机 **`CAB-001-1`（24 格口：6 大 / 8 中 / 10 小）**，请求尺寸 `SMALL`，
每个虚拟用户做一次 `占位 → 取消`（等价于"用户没投件就取消"，让容量能回收，否则测的是卖光）。
只压**分配路径**：计费、押金、开柜指令尚未实现（第 11~13 刀）。

两策略对照，启动时用 `--cabinet.alloc.strategy=pessimistic|cas` 切换：

- **pessimistic**：`SELECT … FOR UPDATE` 锁候选行 → 锁内条件更新
- **cas**：无锁读候选 → 按尺寸偏好顺序逐个条件 `UPDATE … WHERE status='FREE'`（止损上限 6 次）

## 2. 结果

吞吐口径 = **成功占位数 ÷ 成功样本跨越的秒数**；`10409`=真没位，`10410`=抢输了（可重试）。

| 策略 | 并发 | 成功数 | 吞吐(成功/s) | create 成功 avg/p99 (ms) | 10409 数 | 10410 数 | 拒接连接 |
|---|---|---|---|---|---|---|---|
| pessimistic | 100 | 24 | 50.4 | 320 / 428 | 76 | 0 | 0 |
| pessimistic | 500 | 28 | 10.6 | 861 / 1887 | 467 | 0 | 5 |
| pessimistic | 1000 | 34 | 8.4 | 1593 / 3292 | 706 | 0 | 260 |
| cas | 100 | 24 | 34.7 | 457 / 624 | 66 | 10 | 0 |
| cas | 500 | 32 | 11.5 | 1248 / 2145 | 392 | 27 | 49 |
| cas | 1000 | 25 | 6.5 | 976 / 3103 | 610 | 19 | 346 |

**正确性（本刀真正的验收）**：六轮跑完（每策略 1620 个请求）直接查库核对，三项全为 0——

```
oversell（同一格口多条活动单）= 0
dirty（RESERVED 却没绑 current_order_id）= 0
inconsistent（FREE 却被活动单绑住）= 0
```

## 3. 结论

1. **正确性来自结构而不是自觉**：`uk_order_active_slot (slot_id, active_flag)` +
   条件更新 + 单事务，使"超卖"在存储层做不到。两策略、最高 1000 并发都没出现一例。
2. **两种策略吞吐相近（8~50/s 区间），因为瓶颈不在锁算法**：
   连接池 `maximum-pool-size: 10`，事务时长随竞争升到 ~1.6s，
   于是天花板 ≈ `10 连接 ÷ 1.6s ≈ 6 tx/s`，与实测 6.5~11.5/s 同量级——
   **算法差异被池容量和热点行抹平了**。这条推论解释了为什么"换个锁"没带来数量级提升。
3. **真正的差异在失败语义**：CAS 产出 `10410 抢输了`（10~27 例，客户端可立刻重试），
   悲观锁一条都没有——等待锁的线程醒来只能看到 `10409 没位`。**"没位"和"抢输"混在一起，
   客户端就无法决定"重试"还是"换柜机"**，这是选 CAS 的实质理由，不是性能。
4. **1000 并发出现 Connection refused（260/346 例）**：Tomcat accept 队列被瞬时间歇性打满。
   它诚实暴露了一件事——**当前没有任何入口背压**：压测时我把限流关了（见 §4），
   真实环境 `@RateLimit` 开着会先返回 42900 而不是让内核拒接。
   结论：限流是必需的，且需要把 `accept-count` / 池容量 / 队列做成显式配置而不是默认值。
5. **下一步不是"再调锁"，而是把 DB 事务摘出关键路径**（第 10 刀：Redis+Lua 预扣 + 异步落库）。
   预期收益直接由本报告的算术得出：只要事务不再横跨"分配 + 建单 + 回滚"整条链，
   10 个连接的天花板就该被抬高；同时补两组对照——(a) 池调到 30；(b) 流量分散到 3 台柜机
   （真实场景没有这么热的单柜）。

## 4. 口径与不可比因素（不写这段，上面的数字就没有说服力）

- **限流关闭**：`--cabinet.ratelimit.enabled=false`（仅本地；该开关关掉时服务端会打 warn）。
  否则 100 并发里 80 个会被限成 42900，测到的是限流器。
- **单用户 token + 每请求唯一 `requestId`**：幂等不会把并发请求合并掉，
  所以这里测的是并发分配而不是幂等。
- **单柜机热点**是最坏情况；生产上是 N 台柜机分摊，绝对吞吐会更高，
  这里的数字只用于**两策略横向比较**，不是容量结论。
- **压测机与服务端同机**（Windows + 本地 MySQL）：客户端与服务争 CPU/IO，
  高并发段的绝对值偏低；同样是横向比较有效、绝对值不可外推。
- **loops=1，非稳态**：每轮是一次性冲击，不含预热与连接复用稳态；
  第 10 刀补 `duration` 模式的稳态测试。
- 业务码统计口径：JMX 里用 Groovy 后置处理器把 `code` 写进样本标签并把非 0 标为失败
  （因为按约定 `1xxxx` 走 HTTP 200，JMeter 默认会把"没抢到位"算成成功）。

## 5. 过程踩到的两个坑（与业务无关但值得记）

1. **PowerShell 5.1 会静默丢掉 `-Jthreads=$n` 这类"等号 + 变量"参数**，JMeter 收到空值
   → 0 线程 → `summary = 0 in 00:00:00`，看起来像"压测通过"。必须写成引号数组元素再 splat。
2. **`-Jtoken` 传 300+ 字符 JWT 走命令行同样丢**，改用 JMeter 官方的 `-q properties文件` 传，
   并把该文件放在 `stress/results/`（含凭据形态内容，不入库）。
