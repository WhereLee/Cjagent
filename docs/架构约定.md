# 架构约定（底座阶段）

> 本文件是**约定的唯一来源**。后续任何分层、命名、错误码、配置方式的改变，先改这里再改代码。

## 1. 分层与命名

- 包根：`com.wherelee.cabinet`，Maven 坐标 `com.wherelee:cabinet-server`
- 单模块 + 分包（阶段 1 业务变厚后再评估拆多模块），包边界即依赖方向，**禁止反向依赖**：

```
interfaces      对外接口：admin（后台）/ mini（用户端）/ system（自检），两端 Controller 不共用
application     用例编排、事务边界（@Transactional 只在这一层）
domain          实体、枚举、领域服务、仓储接口（不引用任何技术框架）
infrastructure  mapper、缓存、消息、外部 SDK、多租户等技术实现
common          与业务无关的通用能力：响应体、错误码、异常、链路、注解
config          Spring 装配（数据源、MyBatis-Plus、OpenAPI…）
```

- 接口路径按端划分：`/api/admin/**`、`/api/mini/**`、`/api/system/**`
- DTO 进出参不与 Entity 混用；Entity 不出 infrastructure 之外的返回值

## 2. 中间件与数据源职责

| 组件 | 用途 | 库/位置 | 备注 |
|---|---|---|---|
| MySQL 8.0.44 | **业务主库**（唯一被 MyBatis-Plus 接管） | `cabinet_dev` / 测试 `cabinet_test` | `@Primary` 数据源 |
| PostgreSQL 18.3 + pgvector 0.8.2 | agent / 向量检索 | `cabinet_agent` | 只走 `pgJdbcTemplate`，不进 ORM |
| Redis | 缓存 / 登录态 / 限流 | **db 8**，key 前缀 `cab:` | 本机为多项目共用实例，禁止用 db 0 |
| RocketMQ 5.3.1 | 业务异步事件 | namesrv `127.0.0.1:9876` | topic 前缀 `cabinet_`，消费组 `cabinet-*-consumer` |

- **双数据源的事务陷阱**（已踩坑位，勿回退）：Boot 的 `DataSourceTransactionManagerAutoConfiguration` 是
  `@ConditionalOnMissingBean(PlatformTransactionManager.class)`。一旦注册了 `pgTransactionManager`，
  自动配置就退让，`@Transactional` 会静默作用在 PG 上、主库回滚失效。
  因此 `MysqlDataSourceConfig` 显式声明 `transactionManager` 并标 `@Primary`；操作 PG 需事务时写
  `@Transactional("pgTransactionManager")`。
- MyBatis-Plus 3.5.9 起，分页/多租户/防全表更新这类依赖 JSqlParser 的拦截器在独立模块
  `mybatis-plus-jsqlparser`，漏引会在编译期报「找不到符号」。

## 3. 统一响应与错误码

- 一律返回 `R<T>`：`code` / `message` / `data` / `traceId` / `timestamp`；`data` 为 null 时不序列化
- 错误码分段：`0` 成功；`1xxxx` 业务；`4xxxx` 客户端（参数/认证/权限/限流）；`5xxxx` 服务端
- **HTTP 状态按错误码族给**（`GlobalExceptionHandler.httpStatusFor`）：`1xxxx` → 200（请求处理完了，只是结果不满足）；
  `401xx` → 401，`403xx` → 403，`404xx` → 404，`405xx` → 405，`409xx` → 409，`429xx` → 429，其他 `4xxxx` → 400；
  `5xxxx` → 500。前端据此区分“去登录”/“无权限”/“提示重试”，全返 200 就没法区分
- 生产环境 `cabinet.exception.echo-detail=false`，外部只见标准文案，内部堆栈只进日志

### 3.0 两个必须防住的异常处理陷阱（第三刀实测抓到）

- **`@PreAuthorize` 拒绝会被兜底 `Exception` 处理器抢走**，变成 500 + 50000：前端把权限不足当
  “系统异常、稍后重试”，用户重试还是不行；服务端告警也被弄成噪声。
  必须显式写 `@ExceptionHandler(AccessDeniedException.class)`。
- **MyBatis-Spring 会把异常转译成 `DataAccessException`**，埋在 cause 里的 `BizException`（如 40301）
  会被当成系统异常。处理方式：`@ExceptionHandler(DataAccessException.class)` 里沿 cause 链
  最多向下 10 层找 `BizException`，找到就按它的错误码响应，否则才归为系统异常。
- **全局异常处理器只能处理 Controller 内部抛出的异常**：过滤器（Security）里抛的它管不到，
  所以 401/403 的响应体要靠 Security 自己的 `authenticationEntryPoint` / `accessDeniedHandler`
  写（见 `AuthFailureWriter`），两处都要保持 `R` 结构一致。

## 3.1 实体基类与自动填充的坑（集成测试实测抓到）

- `@TableLogic` **只负责查询条件与删除语句，不会在插入时赋值**；想让 `deleted` 在插入后就是确定值，
  必须额外标 `@TableField(fill = FieldFill.INSERT)`。否则靠 DB 列默认值，插入能成功但内存里
  的实体 `deleted` 仍为 null，业务代码紧接着用这个实体就会拿空值。
- `strictInsertFill` / `strictUpdateFill` **只填当前为 null 的字段**。对 `updateTime` 而言这是错的：
  它在插入时已被填过，更新时会被跳过，导致 `update_time` 永远等于创建时间。
  所以 `updateFill` 里用 `setFieldValByName`（无条件刷新）。
- 显式赋值优先：`strictInsertFill` 的"只填 null"特性正好给补录/迁移留了口子（保留原始 create_time）。
- 存储精度：MySQL `DATETIME(3)` 对秒小数部分是**四舍五入**，Java `LocalDateTime` 带纳秒，
  读写一轮会有 ±1ms 漂移；时间列统一用 `DATETIME(3)`，断言用容差而不是等值。

### 3.2 写入侧的租户守卫不能指望插件（集成测试实测出的坑）

真实 SQL 证据：

```sql
INSERT INTO probe_audit (id, name, tenant_id, create_time, update_time, deleted) VALUES (?, ?, ?, ?, ?, ?)
==> Parameters: ..., null      -- tenant_id 为 null 也写进去了，不报错
```

- `tenantId` 标了 `fill = INSERT`，MP 会**无条件把这一列写进 INSERT 语句**；
  `TenantLineInnerInterceptor` 发现列已存在就认为"业务自己给了值"，**既不再注入也不再校验**。
- 后果：无租户上下文时插入不报错，静默写入 `tenant_id = null` 的黑洞数据
  ——不属于任何租户，所有租户都查不到，但占着表。
- 分工定下来：**写入侧（INSERT）的租户守卫在 `AuditMetaObjectHandler` 里做**
  （`BaseEntity` 子类无上下文即抛 `BizException(40301)`）；
  **读/改/删侧由 `TenantLineInnerInterceptor` 做**（它会给 where 拼上 `tenant_id = ?`，
  没有上下文则拒绝执行）。两边各自成立，缺一不可。
- 测试含义：这类漏洞单租户环境永远测不出来，必须**同时存在两个租户**才能断言隔离是否真生效。

## 3.3 分页与排序（第5刀）

- 入参统一 `PageQuery`（`pageNum` / `pageSize≤200` / `orderBy` / `asc`），出参统一 `PageResult`
  （`pageNum/pageSize/total/pages/records`），**不返回 hasNext 之类派生字段**
- 转换只走一处：`PageSupport.toPage(query, 白名单)`；`common` 不依赖 MyBatis-Plus，
  所以 ORM 换掉也不动接口契约（ArchUnit 有机检规则）
- `orderBy` 传**实体属性名**而不是列名：不暴露 schema，且白名单可按属性校验
- 排序要过两道关：形状检查（`^[a-z][a-zA-Z0-9]{0,63}$`）+ **每接口声明的白名单**。
  只做形状检查仍不够：合法列名一样能排出不该看的信息。`order by` 拼的是标识符，
  预编译语句帮不上忙，这是真正的注入口
- 报错不回显可用排序字段（否则等于送一份可猜字段的探测表）
- **接口不指定排序时必须兜底一个稳定排序**（默认 `id desc`）：MySQL 无序分页会让记录
  在翻页时被跳过或重复出现，这种 bug 在测试库里几乎看不出来
- 查询接口不加 `@OperationLog`：只读请求进审计会快速灌满表格，抬高噪声后真正该看的写操作没人看

## 3.4 安全默认拒绝（第5刀）

- 四条安全链：`@Order(1)` 公开（`/api/system`、`/api/public`、`/actuator/**`、文档、`/error`）
  → `(2)` admin → `(3)` mini → `(4)` **兜底 `/**` 一律要求已认证**
- 兜底链必需：多个 `securityMatcher` 只处理各自匹配的路径，没被任何链命中的请求会**绕过整套安全过滤**。
  新加一个接口、写错一个路径前缀，就是个无鉴权入口；默认拒绝把“静默暴露”变成“401，立即看得见”

## 3.5 业务地基（V4）踩到的四个坑（第8刀，均为实测而非推演）

1. **MyBatis-Plus 默认不写 null 字段**：`updateById` 会跳过值为 null 的属性。于是
   “把 `active_flag` 置 NULL 以释放唯一索引占位”这个动作被**静默丢掉**：单子进了终态，
   格口却永久不可用——比超卖更隐蔽。凡“置 NULL 本身有业务含义”的列，必须
   `@TableField(updateStrategy = FieldStrategy.ALWAYS)`。
2. **不能用“同一会话读两次”模拟两个并发者**：MyBatis 一级缓存（同一 SqlSession）会返回
   **同一个对象实例**，第一次更新抬了 version，第二个“并发者”跟着变新，乐观锁冲突根本没产生。
   测并发写必须**手拼一个陈旧实体**（只带 id + 旧 version + 要改的字段）。
3. **小表上 EXPLAIN 断言不可靠**：24 行时，“只按 status 过滤”也会选复合索引
   （`access_type=index`，全索引扫比扫聚簇索引便宜）。断言**索引形状**（查
   `information_schema.STATISTICS` 的列序）是确定性的；“优化器用不用”等有量级数据后再断言。
4. **种子脚本要“收敛”而不只是“不报错”**：`ON DUPLICATE KEY UPDATE` 只写主键冲突不报错，
   但没列入更新列表的列会**停在旧值**（改了分配规则重跑，slot_id 仍为历史值）。
   凡生成结果字段都要在 ON DUPLICATE 里重写一遍。

另外一条结构性规则（与逻辑删除交互）：**活动单不得被逻辑删除**。`deleted=1` 不会把
`active_flag` 置 NULL，唯一索引仍占位 → 格口永久不可用。所以“归档/作废”必须先转终态再删，
不得直接 removeById。

## 3.6 并发分配与异步落库约定（第10刀）

- **分布式锁必须在事务之外**。MySQL REPEATABLE READ 的一致性快照在事务的**第一次读**时就定了；
  如果锁在事务内才拿到，持锁者读到的仍是上一个事务提交前的旧数据，**锁只挡住写入、挡不住旧快照的读**。
  因此柜机锁由 `CabinetLockGuard` 包住整个用例（在 Service 的事务外），分配器自己不加锁。
  这一条是用失败测试换的，不是背出来的
- **进租户白名单 ≠ 写入免上下文**。白名单只影响 `TenantLineInnerInterceptor` 的 SQL 注入；
  `AuditMetaObjectHandler` 的写入守卫是独立的一层。守卫的语义是“**绝不写入 NULL 租户**”：
  实体已显式带 `tenantId` 就接受（消费者/定时任务场景），两者都没才拒绝
- **预扣用集合不用计数**：计数会漂（重复归还凭空造出可卖位 = 超卖；崩溃与漏消费让计数长期偏低 = 少卖）。
  `SPOP`/`SADD` 的成员只能来自 DB 真相同步，**多卖在结构上做不到**；少卖靠 `syncFreeSets` 校准收敛
- **预扣 fail-closed，限流 fail-open**。预扣挂了放行等于把全部压力直接砸到热点行（雪崩）；
  限流挂了只是少一层保护。两者故障策略相反是故意的，不是写法不一致
- **MQ 消费约定**：异常必须上抛（吞掉 = 告诉 broker 成功 = 静默丢单）；幂等键用**业务单号而不是 msgId**
  （重投时 msgId 会变）；已 PROCESSED 的记录不得被写回 FAILED；
  **幂等表只降低重复处理概率，唯一索引才保证重复不发生**，两者不能互相替代
- **消息里的 `tenant_id` 是信任边界**：谁能写这个 topic，就能以哪个租户身份落库。
  topic 只允许服务自己写，且 broker 不得对外网开放（第 16 刀的 TLS/ACL 负责）
- **异步路径的中间态不假装成终态**：响应给前端的 `PERSIST_QUEUED` 不是 `OrderStatus` 成员
  （DB 此时确实无行），不得为了“界面好看”把它硬说成 RESERVED
- **测试必须跑在真实入口上且不额外包上下文**：并发用例走 `StorageOrderFacade`（直调 Service 会
  跳过柜机锁）；消费者用例**不在外面包 `runAs`**（建上下文是被测行为），包一层就会把上面那个守卫 bug 遮成假绿；
  同一 JVM 的消费者会与用例赛跑，所以业务用例不发消息，端到端由真实 HTTP 手工验证

## 3.7 设备通道与故障处置约定（第11刀）

- **业务只依赖 `DeviceChannel` 端口**，模拟器与未来的 MQTT 实现都在 infrastructure。
  容错逻辑（幂等、超时、乱序、故障处置）**一律不得写在通道里**：否则换协议时这些逻辑会被丢掉
- **等回执不得持有事务与连接**：用 `TransactionTemplate` 拆成“写指令”与“收敛回执”两个短事务，
  中间等待不占连接（第 9 刀压测的瓶颈就是池 10 × 事务时长）。代价显式承认：中途崩溃会留下
  “设备开了门但订单未变”的现场，靠上报流水 + 超时回扫收敛（第 13 刀）
- **requestId 形如 `单号:动作:第几次`**：只写“单号:动作”会让重试拿回上次失败结果（重试通道被自己堵死），
  完全随机则拦不住双击。同一尝试幂等、不同一尝试换新键
- **失败处置的判据是“正在执行哪个动作”，不是“当前状态”**：
  `OPEN` 失败→件还在用户手里→退回 `RESERVED` 可重试；`CLOSE_VERIFY` 失败/谎报→件已在柜内→`ABNORMAL` 等人工；
  `OPEN_TEMP` 失败→件未丢→保持 `ACTIVE`。用状态做判会恰好把两者弄反（本刀实测踩过）
- **指令层 SUCCEEDED 不等于业务层成功**：设备自述成功但门磁未确认时，指令记 SUCCEEDED、
  订单记 ABNORMAL。混淆这两个层次就会出现“系统认为已关门、件其实还在柜里”
- **上报幂等用 `dedup_key = cmd:<requestId>`，不能拿设备侧 `seq` 当判据**。
  曾经的写法是 `cabinetId:seq` + “seq 不高于已记录就当旧事件丢弃”——看着正确，实则生产必炸：
  设备重启/刷固件会把 seq 归零重发，于是重启后第一条**正常**回执撞上历史唯一键被当重复丢弃，
  表现为“柜机上线后所有开柜都不生效”。现在 `seq` 仍然入库（对账与人工排查用），
  但**只用于参考，不决定业务能否推进**；“旧事件”的判据回归到“同一条指令的回执重复送达”。
  此缺陷由 dev 环境端到端验证发现，**集成测试每个用例新建柜机，恰好盖不到**——
  共享柜机/共享设备序列号跨用例的场景必须有一条真链路跑（已补进 `scripts/verify-funds.ps1` 的教训）
- **上报的两个时间列不得混用**：`received_at` 是权威时间（判定与计费），`reported_at` 只用于对账
- **连续失败停用存在 Redis**：它是易失运行态，不需历史也无需事务；达阈值→格口 FAULT + 柜机 DISABLED +
  故障事件（事件里存当时 failCount，否则事后无法还原判定依据）
- **模拟器只注册 dev/test/integration**：prod 没这个 bean，装配会直接失败而不是默默降级

## 3.8 资金与账本约定（第12刀）

- **金额一律整型点数（1 点 = 1 分），全链路不得出现浮点**。浮点会在累加时产生分厘误差，
  而这种误差在钱上不是“精度问题”是“对账对不上”
- **一笔流水只影响一栏**（可用或冻结），符号由类型定（`PointTxnType`）。
  这是让不变量 3 能写成两条**纯求和**断言的前提；一旦允许一笔跨两栏（“冻结”写成一条），
  `Σ流水 == 余额` 就不再成立，只能靠人工推导。“冻结”拆成 `FREEZE_OUT + FREEZE_IN` 两笔
- **余额靠条件 UPDATE 守卫（`points + delta >= 0`，看影响行数），不靠先查后改**；
  DDL 上的 `CHECK` 是第二道，两者都要：只靠 CHECK 会在并发下形成异常风暴，
  只靠条件更新则挡不住下一个改代码的人
- **流水只增不改**：写错就再记一条 `ADJUST` 冲正。一旦流水可改，“按流水重算余额”这个
  自证手段就废了。`balance_after` 是给人看的快照，不是真相
- **幂等下沉到索引**：`uk_txn_biz(biz_type, biz_no)` 才是“同一业务事件只入账一次”的最终裁判；
  代码里先查一次只是为了省锁。充值用**通道流水号**、订单动作用**单号:动作**做 `biz_no`
- **展示层的编码器不得用来序列化业务算术数据**：容器里那个 ObjectMapper 为了防前端精度丢失
  把 `Long` 全局编成字符串，拿它写定价快照就让 `unitPointsPerHour` 变成 `"25"`，结算读不回来
  （第 12 刀实测）。内部算术快照用自己的 mapper
- **“余额不足”在结算里是业务分支，不是异常**：`tryPost` 返回状态而不抛。
  因为嵌套调用同一事务的 `@Transactional` 方法抛出异常会把物理事务标成 **rollback-only**，
  外层接住也没用，提交时必爆 `UnexpectedRollbackException`（第 12 刀实测）
- **欠费不锁件、押金不抵欠费**（防呆红线，S-03）：扣不到部分记 `arrears_points`，
  仍然放行取件并退还押金；追缴交给风控/调度，不拿用户的东西做抵债
- **取消与取件的退款必须走同一段代码**（`unfreezeAndRefundDeposit`）：两处各写一遍的后果是
  “改了取件忘了取消”，形成押金悬挂（不变量 4）。状态推进用条件更新（`where status='HELD'`），
  退两次押金比超卖更贵
- **结算只能读 `pricing_snapshot` 里的单价**，不能读当前配置：改价不得追溯影响已发的单。
  快照同时是审计材料与计算输入，而不只是“留个记录”

## 3.9 延迟任务与调度约定（第13刀）

- **真相源只有一张表**：`biz_delay_task` 上的条件更新决定“谁执行”；MQ 定时消息、Redis ZSet、
  扫表轮询都只是**提醒**。因为跳存储没有事务，“Redis 认为发了、MQ 认为投了”不能当执行权
  （否则同一任务跑两遍，或谁都没跑）
- **提醒可以丢、可以重，但不能推后已排好的时刻**：`ON DUPLICATE` 对 `PENDING/FAILED` 只取
  `least(fire_at, new)`；`RUNNING` 不动；`DONE` 是新一轮起点，取新值并把 `attempt` 归零；
  `DEAD` 永不静默复活（复活一条判死任务会掩盖真问题）
- **MySQL `ON DUPLICATE KEY UPDATE` 按从左到右赋值，后面的表达式读到的是前面的新值**：
  所有“按旧 `status` 分流”的 `case` 必须写在 `status = ...` 前面。本刀写过
  `attempt = case when status='DONE' then 0 ...` 在 `status=` 之后——归零永远不成立，不报错（实测）
- **可抢判据必须包含 `FAILED`**：失败退避后写的就是 FAILED，候选查询只认 PENDING 会让重试
  永远跑不到且不报错，外表看是“还在重试”实则任务躺在库里到地老天荒
- **三个事务边界是刻意的**：① 抢批（`FOR UPDATE SKIP LOCKED` + 条件更新）一个短事务；
  ② 业务 + `markDone` **同一事务**（否则“做完但状态没落”= 双执行）；③ 失败回写（attempt/退避）
  **另起事务**，不然业务回滚会把退避证据一起抹掉，指数退避形同不存在
- **`TaskHandler.transactional()` 默认 true，但要等外部 I/O 的 handler 必须标 false**：
  `TransactionTemplate` 在 `@Transactional` 方法内**不会新开事务**（`REQUIRED`），外层一开就把
  “等回执不持事务”重新合上（第 9 刀量过的连接池瓶颈形态会直接复发）。代价显式承担：
  **标 false 的 handler 必须完全可重入**（每一步都是条件更新/幂等键）
- **worker 跳租户读、业务带租户写**（两个方向相反）：抢占与取任务行都要 `@InterceptorIgnore`，
  否则调度线程无上下文会被守卫拒执——**后台轮询一个任务也执行不了且不报错**（本刀实测，
  靠“不关 poll 的那条用例”才暴露）；handler 的业务副作用必须在 `runAs(task.tenantId)` 里跑
- **对账只报告不改钱**：差异进日志与 Gauge（Gauge 读**上一次作业的结果**，不现算，否则抓取自已在打垮被监控者）；
  动钱只能人工 ADJUST（留操作人）。需要补救的差异（如悬挂押金）由对账**现场登记重试任务**，
  而不是在下单时预防性排好——每张单都排一条“未终态→重试→判死”会把 DEAD 变成噪声
- **失败处置看“正在执行哪个动作”，不看当前状态**（第 11 刀结论在调度侧同样成立）：
  指令回扫的 OPEN 失败退回 `RESERVED`、`CLOSE_VERIFY` 失败转 `ABNORMAL`，与实时路径共用同一张映射表
- **不无限看管**：逾期任务要么命中“价格已到顶”（读快照里的 `cap-days`），要么命中
  `stranded-days` 硬兑底，两者任一就停止续排并响 ERROR；**“每小时续排直到终态”在没有终态的单上
  就是一张永远没人接的工单**
- **注解不能谎报语句类型**：用 `@Update` 承载 `INSERT ... ON DUPLICATE KEY UPDATE` 会让
  `BlockAttackInnerInterceptor`（只处理 UPDATE/DELETE）去解析这条 SQL，碰上
  `JsqlParserSupport.processInsert` 的默认实现直接抛无信息的 `UnsupportedOperationException`——
  表现为“下单必炸”而堆栈指不到原因（本刀实测）
- **MySQL 的 `ON DUPLICATE KEY UPDATE` 按从左到右赋值，后面的表达式读到的是前面已赋的新值**：
  凡“按旧列值分流”的 `case` 必须排在被改写的那个列之前。本刀把 `attempt` 的归零写在
  `status` 之后，`status='DONE'` 从此永不成立，归零静默失效（不报错）
- **中间件的隐式推导值要显式定住**：Redisson 默认重试策略带抖动随机，而它用这个随机值推导
  `HashedWheelTimer` 的 tick，抽到某些值就是 0 → 启动抱 `tickDuration : 0`（约 1% 的启动会中）。
  启动能不能成功不该交给随机数
- 三实现对比、实测延迟与档位量化误差表：[`调度三实现对比.md`](./调度三实现对比.md)

## 3.10 门态、物检与异常约定（第 13B 刀，规则见 docs/门态与物品争议设计.md）

一个格口上有**三个正交事实**，分开存、不许挤进同一个字段：

| 字段 | 回答的问题 | 归谁管 |
|---|---|---|
| `status` + `current_order_id` | 能不能卖、被哪张单占着 | 分配器与订单 |
| `door_open_at` / `door_closed_at` / `_by` | 门开着没、开了多久、谁开关的 | CompartmentStateService |
| `presence` + `presence_checked_at` + `anomaly` | 里面有没有东西、因此算哪类异常 | 同上 |

- **“可分配”只有一个定义**（`SlotCandidateQuery`）：`status=FREE 且 门已关 且 无异常`。
  四个分配器 + 预扣空闲集合 + 定时校准全部走它。**Java 侧的 `BizCompartment.assignable()` 与它同判据**；
  两边不一致时“挑得到但写不进”或“写进去了不该分”，后者就是把锁不上的格子卖给用户。
  预扣只认 Redis 集合不查 DB，所以**集合是这套约定里唯一能造成卖错的地方**（已验证进用例）。
- **门态与异常都写成条件更新**，不“反正盖写一次”：`markDoorOpen` 带 `door_open_at is null`，
  重复回执/重试只会影响 0 行。起点被刷成“刚开”就是把已发生的 30 分钟免掉——**这些列记的是钱的地基**。
- **计费起点 `started_at` 落定后不再改**（不变量 I10）：取 `min(关门时刻, 容错到期时刻)`；
  容错到期时刻存**在单上**（`tolerance_until`）而不是现算配置，否则改容错会追溯改掉进行中的单。
- 异常解除只允许 `DOOR_OPEN` 自动（门关即清）；其余三类**只能由人**放行（I9）。
  自动解除**只看门不看物**：拿“测不到东西”卡解除，没装物检的柜机（现实中的大多数）会整柜永久不可用。

本刀七个实测坑（都不是推演出来的，每条都先红过一次；6、7 来自 13C）：

1. **模拟器里“先改物理”还是“先算回执”不是风格问题**。把 `applyPhysics` 挪到 `receiptFor` 之后，
   算门磁确认位时读到的还是开柜留下的“开着”——**每一次正常关门都被报成谎报**（五条用例同时红）。
2. **一个故障只能影响它那一维**。先写成“只有 NORMAL 才动物理”，结果序号注入（STALE_SEQ）顺带把门变成了
   没关；再把 `SENSOR_NO_ITEM` 落到 default 之外，又让“没有物检”把门态一并报坏。注入正交性靠代码保证，
   不靠注释提醒。
3. **准入判据要看物理事实而不是只看状态**：容错期满巡检会把单推到 `ACTIVE`，如果关门校验只允许
   `OPENING/TEMP_OPEN`，那“门开着超时了、人又回来关上”这条必然发生的路就推不动了。
4. **共享环境里的全局断言是雷**：“整个 ZSet key 为空”“全库账户必须平”“两个事务各拿 4 条”这类断言
   在赌别人不写数据。本刀又踩到一次（zset 触发用例），改成只断言**本用例自己的成员**。
5. 删掉的 Flyway 文件会**留在 `target/classes/db/migration`**，下一次不 clean 就出现“Found more than one
   migration with version 10”，症状是整个上下文起不来、146 条用例一起错。改过迁移文件名后要 clean。
6. **`REQUIRES_NEW` 写完的东西，会被外层的全行 `updateById` 抹掉**（13C 实测）。
   外层事务的快照定在内层提交之前，重新加载读到旧值，紧接着的全行更新把刚写的复审次数写回 0。
   修法是让**编排方法不开事务**（denyItem），两个写入各自成事务、顺序自然成立；
   别指望“记得只更部分列”——那只能防一次，防不住下一个人。
7. **全局扫表类机制的用例要跑到“出现”为止，不能只跑一轮**：`runDue` 每轮只按 `fire_at` 取 `batch-size` 条，
   共享测试库里只要别人的到期任务排在前面，我们那条本轮就压根不会被认领（表现为“扫街没登记回扫”）。
   这类“我的那条何时被处理”的断言，本质上都需要一个有上限的等待循环。

## 4. 链路追踪与日志

- `TraceIdFilter` 最高优先级执行：沿用合法的 `X-Trace-Id`（8–64 位 `[0-9A-Za-z_-]`，防日志注入），否则生成
- traceId 进 MDC → 日志 pattern `[trace:%X{traceId:-none}]`，并回写响应头；`R` 自动带出，前端报障可直接给 ID
- 日志目录 `logs/`（已 gitignore）：`cabinet-server.log` 按天+50MB 滚动、留 15 天封顶 1GB；`cabinet-server-error.log` 只收 ERROR，留 30 天
- **线程池/异步必须传递 MDC**，否则子线程日志丢 traceId（用到异步时统一走装饰过的 Executor，不裸用 `new Thread`）
- **耗时不做成响应头**（实测坑）：Spring 写回 body 时会 flush，响应在控制器返回时就已 committed，
  filter 在 `finally` 里 `setHeader` 会被容器**静默丢弃**；而 MockMvc 的 mock response 不真提交，
  所以断言会假绿。耗时只看服务端日志（`AccessLogFilter`，慢请求升 warn）与 Nginx `$request_time`，
  聚合统计用 actuator 自带的 `http.server.requests` 指标
- 写响应头必须在响应体之前：任何“后置往响应里补东西”的设计（包 header、包状态码）都要先问一句
  “此时响应 committed 了吗”

## 4.1 JVM 参数与指标暴露（第5刀）

- **JVM 参数单一来源 `deploy/jvm.opts`**：本地 `scripts/run-app.ps1` 与第8刀的 systemd 单元都读它，
  不存在“本地一套参数、线上另一套”。含 `-Xms/-Xmx`、Metaspace 上限、OOM 时 heap dump + 快速退出、
  GC 日志滚动输出
- 它**不叫 `*.env`**：本仓库里 `.env` 的含义是“密钥、绝不入库”，已提交的参数文件不能占同一个
  名字空间，否则“密钥只进 .env”这条例和推前必查的扫描模式都会被混淆
- 指标**只埋不采**：dev 额外暴露 `metrics` 与 `prometheus`（实测 `curl /actuator/prometheus` = 200，
  `jvm_memory_used_bytes` 可取）；prod 的 `exposure.include` 只留 `health,info`
- 靠 exposure 而不是靠安全规则：**未暴露的端点根本不存在**（`heapdump`/`env` 这类经典泄露点直接消失），
  安全规则会漏，白名单不会
- MockMvc 验不了 `/actuator/prometheus`（靠内容协商输出文本格式，无 Accept 头时 404），
  指标存在性改用 `/actuator/metrics` 断言；文本端点由真实 curl 验证

## 4.2 切面顺序与故障策略（第四刀）

执行顺序由外到内（`@Order` 已固定，**不要改数值**）：

```
TraceIdFilter(HIGHEST+10) → AccessLogFilter(HIGHEST+20) → Security 过滤器链
  → @OperationLog(-200)      审计：最外层，连被鉴权拒绝的尝试也要留痕
  → @RateLimit(-150)          限流：先挡量，不消耗下游资源
  → @Idempotent(-100)         幂等：只对真正要执行的请求占位
  → @PreAuthorize             Spring Security 方法级鉴权
  → @Transactional            事务边界（只在 application 层）
  → 业务方法
```

为什么负值：Spring Security 的方法级拦截器默认落在正数区间，我们的切面取负才能包在它外面；
否则“权限不足被拒”这种恰恰最该记审计的调用根本进不到切面里。

| 切面 | Redis/DB 不可用时 | 为什么 |
|---|---|---|
| `@RateLimit` | **fail-open**（放行 + error 日志） | 限流是保护措施不是访问控制；它故障时把整站变成 500 是更大的事故 |
| `@Idempotent` | **fail-closed**（拒执行，报 50100） | 幂等是正确性约束，无法判断是否重复时放行会重复下单/重复开锁 |
| `@OperationLog` | 不向上抛，只记 error | 审计写失败不该打挂用户请求；代价是**审计不保证强一致**，不得用作计费/对账依据 |

脱敏两条路都要有：出参用 `@JsonMask`（标在 VO 字段上），日志/审计入参用 `MaskUtils`
（按**字段名**识别，含嵌套与数组，命不中则全遮兼容脏数据）；只做其中一条等于另一半仍为明文。

## 5. 配置与密钥

- `application.yml` 公共项 + `application-{dev,prod}.yml` 差异项；prod 不给地址/账号默认值，缺失即启动失败（fail fast）
- 本地密钥来源 `server/.env`（properties 格式，经 `spring.config.import=optional:file:.env[.properties]` 注入），
  `.env` 已 gitignore，模板是 `.env.example`
- `.env` 是 **properties 格式**（Spring 按 ISO-8859-1 读），所以**值里不要写中文**，注释也别用全角标点开头；
  需要中文说明请写到 `.env.example` 以外的文档里
- HikariCP 走 `@ConfigurationProperties` 直接绑定，属性名是 `jdbc-url` 而不是 `url`（写错会静默连不上）
- `springdoc.swagger-ui.groups-order` 在 2.8 是枚举 `asc/desc`，不是旧版 `alpha`（写错会让上下文启动失败）
- **本地端口分配**：后端 `8080`、admin 前端 `8082`、mini 的 H5 `8083`（5173 作为兼容项也在 CORS 白名单里）。
  **8081 已被本机 RocketMQ 5 的 proxy 组件占用**（监听 `::8081`），vite 抢它时报的是
  `EACCES: permission denied` 而不是 `EADDRINUSE`，很容易误判成权限问题——
  先查 `Get-NetTCPConnection -State Listen -LocalPort 8081` 的拥有者再改配置
- **JSON 里的数字与字符串**：ID 字段声明为包装类型 `Long`（全局序列化成字符串，防 JS 精度丢失），
  计数与时长声明为原始 `long`（保持 JSON 数字）。**不得给 `Long.TYPE` 也挂上 ToString 序列化**，
  否则分页的 `total` 会变成 `"1"`，而前端类型写的是 number
- 上面这条是真实 HTTP 测出来的：`jsonPath(...).value(1)` 对 number 与 string 是**宽容比较**，
  MockMvc 下永远绿。涉及类型契约的断言必须用 `isNumber()` / `isString()`，不能用 `value(...)`

## 6.1 前端（admin）门禁（第6刀）

- 三道门禁都要为零告警：`npm run lint`（`--max-warnings 0`）、`npm run typecheck`（vue-tsc）、`npm run build`
- **`src/components.d.ts` 与 `src/auto-imports.d.ts` 必须入库**：它们由插件生成，
  而 typecheck 在首次构建前就要看到它们；不入库则新 clone 必红
- 按需引入的两个坑：直接 `import` 的 API（`ElMessage`）与指令（`v-loading`）**不走组件解析器**，
  样式/注册必须手工补，否则是"不报错但没样式/不生效"这种静默失效
- `no-undef` 在 ESLint 里关掉：这事情 TypeScript 已经做了，留着只会对 `window`/`localStorage` 误报
- 验证顺位：先看真实 HTTP（curl 走前端的请求序列），再看界面。只验 build 不算联调
- **路由守卫不能把非凭证失败当未登录**：`/me` 报错时一律 `clear()` + 跳登录，会让网络抖动、
  后端 5xx、超时都把凭证有效的用户踢回登录页，表现为“登录明明成功又退回来”且无线索。
  只有 40100 才清登录态；其余保留登录态并告知原因（服务端才是门禁）
- **防重复提交标志位必须在任何 `await` 之前同步置位**：先 `await validate()` 再置 true 的写法，
  同一个 tick 内多次触发（Enter + 连点）都会读到 false 而全部放行（浏览器实测能打出 3 次 login）
- 展示型页面不得与自己的数据不一致：健康检查只渲顶层组件时，MySQL/PG 藏在 `db.components` 里不显示，
  而页面文案写着“四项都展示”——界面自己说自己的谎。约定：组件树展平到叶子，无关的系统组件（ping/ssl）不展示

## 6.2 用户端（mini）约定（第7刀）

- 版本必须一起锁：`@dcloudio/*` 用同一个日期式构建号（当前 `3.0.0-5020620260917001`），
  `vite` 必须是插件 peer 要求的 **5.2.8**，`@dcloudio/types` 也是精确版（`^` 会 ERESOLVE）；
  `vue-tsc` 要 2.x——1.8 与新版 TypeScript 不兼容（报 `Search string not found`）
- **后端禁用 PATCH 动词**：`uni.request`（小程序侧）的 method 枚举不含 PATCH。
  这一条现在写死成本为零，接口发出去再改就是两边兼容矩阵
- `uni.request` **业务失败不抛异常**（非 2xx 也走 success 回调）且无 params 序列化，
  所以 HTTP 状态与业务 code 必须在请求层分开处理，查询串自己拼（空值要跳过）
- 小程序没有 vue-router：鉴权拦在页面 `onShow` 的 `ensureAuthenticated()`（体验）
  与后端每个接口的 `hasRole('RIDER')`（安全）两处；凭证失效用 `reLaunch` 回登录页，
  目的是**清掉整条页面栈**，否则用户按返回会再撞一次 401
- **登录判定必须是函数，不能是缓存的 computed**：`computed(() => Boolean(readAccessToken()))`
  读的是 Storage（非响应式源），无依赖可追踪 → 只求值一次、永不失效，退出登录后仍为 true；
  叠加“`loadProfile` 无 token 时静默 return null”，导致**仅改 hash 直达受限页完全不拦**
  （浏览器实测 2/2 重现，冷启动却正常，因为 store 重建）。规则：
  非响应式源要么写成函数，要么先把它镜像进 `ref`；回源失败要**抛错而不是返回 null**
- 客户端可见文案不得夹带内部实现细节（曾经出现过：登录页写“后端把它当 openId 用”、
  首页写“阶段 1 第 8~12 刀”）；也要避免把状态渲染成假数据：“未登录/没拉到数据”不能显示成“账号已冻结”
- 实体不得直出：`/api/mini/auth/me` 回 `CustomerView` 而非 `BizCustomer` 实体（openId/unionId/deleted 不下发），
  ArchitectureTest 有机检规则禁止 interfaces 依赖 domain.entity
- 跳转目标必须写**字面量**（`uni.navigateTo({ url: '/pages/x/index' })`）：
  页面流转图生成器靠静态扫描，写成变量会让检查失明（已实际踩到：变量写法导致两个页面被误报不可达）
- H5 的 mock 登录 code 必须**稳定**（存本地）：每次新生成等于每登录一次就注册一个新客户

- **`reLaunch` 会被“上一跳未完的页面过渡”丢弃**（H5 实测：标签页隐藏时 rAF 被冻结、
  或 300ms 内连发导航），结果是“地址栏停在受限页 + 整页空白”。两手都做：
  ① 鉴权回登录页统一带 `animationDuration: 0`（消除动画窗口，不是为了让页面“切换更快”）；
  ② 页面不只依赖导航——`ready` 为 false 时渲染 `<need-login />` 兜底块，让用户能主动点走。
  **不得把正确性完全压在导航成功上**
- 自定义组件走 easycom 约定：目录 `src/components/名称/名称.vue`，模板里直接写 `<名称 />`，不手动 import

## 7. 已记录的简化项（按红线要求显式登记，待办由用户拍板）

| 项 | 简化成什么 | 企业标准 | 影响 | 何时补 |
|---|---|---|---|---|
| 客户归属 | 首次登录由前端传 `tenantCode` | 扫柜机码带过来的站点/运营商归属（或 appId → 租户映射） | 前端传值可被伪造（只能影响新注册归属，老账号改不了） | 第 15 刀扫码流程上线时替换 |
| 小程序微信校验 | dev 开 `mock-login`（code 直接当 openid） | 真实 code2session 验签 | 开关开着等于登录不设防（已用 `@Profile("!prod")` + 配置双保险） | 有 AppID 后关掉 |
| refresh 多设备 | 同账号只记一个有效 refresh | 集合存储支持多设备并发在线 | 手机+平板同时登录会互相顶下线 | 用户体系扩大后 |
| 权限变更生效 | Redis 缓存 TTL 5 分钟 | 变更即广播失效 | 改权限后最坏 5 分钟内旧权限仍可用（需主动 evict） | 后台角色维护功能落地时 |
| JWT 密钥强度 | HS256 对称密钥 | 多实例/多服务共享时用 RS256 非对称 | 目前单服务，够用；接 Java agent 多服务时要换 | 阶段 3 |
| RocketMQ 可靠性 | 仅 producer 配置 + 集群健康检查，无消费者 | 死信队列 + 重试策略 + 消息幂等表 + 轨迹 | 无真实异步场景可验证 | 阶段 1 出现业务事件（订单状态、开锁结果）时 |
| 接口安全 | 无 | `@Idempotent` / `@RateLimit` / `@OperationLog` + AOP 已接（第四刀） | 幂等未写业务键时退化为用户+URI+入参哈希 | 下单/开锁/退款类接口必须显式 `key` 且 `requireKey=true` |
| 集成测试环境 | 本机真库代替容器 | Testcontainers 隔离环境 | CI 与本地行为不一致（版本漂移） | CI 搭建时 |
| 前端 token 存放 | access/refresh 均存 localStorage | refresh 放 httpOnly + SameSite Cookie，access 只存内存 | XSS 一旦发生，两个 token 都能被读走 | **接真实用户数据前必须换** |
| 前端测试 | 只有 lint + 类型 + 构建门禁 | 组件/交互测试（Vitest + Playwright）与后端契约测试 | 登录、权限菜单、分页这些流程目测不测，改动可能默默坏 | 阶段 1 有真实业务页时 |
| 前端请求层 | admin（axios）与 mini（uni.request）**各一份** | 共享核心包 + 平台适配器（transport adapter） | 错误码分派、401 刷新去重这些语义改一处要改两处，有漂移风险 | 接口数明显变多（>30）或出现过一次漂移事故时抽 `packages/api-core` |
| 流转图与页面标题 | `pages.json` 为唯一来源，图由脚本生成 | 设计工具（墨刀/Figma）维护原型 | 图只反映代码事实，不反映设计意图（需求与实现的差异靠 PRD 补） | 需求变多、需要与非技术角色对齐时再引原型工具 |
| 支付通道 | `PayChannel` 抽象 + `MockPayChannel`（`cabinet.pay.channel=mock`） | 真实支付宝/微信下单 + 异步回调 + 验签 + 对账单拉取 | 通道没确认收款就不入账这条已可测；真实通道的重试语义（超时、未知态、重复回调）本刀只能模拟 | S-11：项目最后（受资质与公网回调限制） |
| 滞留单出口 | 停止续排 + `log.error` + 指标计数 | 异常工单队列（派人、超时升级、回写处置结果） | “数得出来”不等于“有人去处理”，运营得自己看看板 | 第 14 刀后台 |
| 逾期未取的“提醒” | 只把单推到 `EXPIRED` + 指标，没有推送渠道 | 短信/微信订阅消息/公众号模板消息 | 用户不主动看页面就不知道已逾期（本项目无推送资质与公网域名） | 接真实通道时一并接 |
| 门未关的处置 | 不再转人工：容错期满后起计 + 标 `DOOR_OPEN` 异常 + 续排提醒，封顶后转台账 | 原规划 §5.6 写的是“自动撑销”（解冻、释放、退押金） | **这是改判不是简化**：自动撑销会把可能真有件的格口标成可分配，而全城多点位派一次人工的成本高于格口被占的损耗（用户 2026-10-09 定，S-16） | 不需补；争议阶梯见 13C |
| 柜内“无物”的凭据 | 现场结束遇到“测不到”（物检坏了/离线/结论超龄）时：**不拦人，但格口标为待确认清空**；远程结束同样拒 | 每次关门拍照 + AI 识图交叉判定（13C 的争议阶梯） | 不对称的不是“信不信人”，而是**人不该被一台坏传感器钉在柜机前，而格子不能无凭据地回到可售池**。我上一版把它当成“大多数柜机只有门磁”的常态并直接采信用户声明——那是自己造问题，而且漏掉了锁格，已于本刀修正 | 13C 接红外→AI→人工阶梯；真接设备时补拍照 |
| 异常原因码 | `anomaly` 只覆盖“门与物”四类；`fault_type` 不新增枚举值（靠 reason 文字区分） | 每个异常类别都有独立可查询的类型值 | 台账按类型聚合时只能靠 reason 模糊区分；但“哪一类”的权威在 anomaly 列上，两处各建一套枚举更容易漂 | 第 14 刀业务运维排班上线时看要不要拆 |
| 待确认清空自动放行 | **不做**：`CONTENT_LEFT`/`CONTENT_UNVERIFIED` 只能由人解除 | 超时自动回到可售池（容量优先） | 代价明写：一台柜机的可用数会因少数没关好的门而下降 | 不补。少卖是钱，卖错是事故（第 16 刀业务运维清单上线后仍然不自动） |
| 对账驱动表 | 以**账户表**为驱动分批扫（余额 vs Σ流水） | 同时以**流水表**为驱动（流水在而账户行被删/被改归别的租户） | 后一种形态本刀不覆盖（需要流水侧另一个游标，千万行上代价不同） | 数据量上来后按流水侧补一批 |

## 8. CI

- 工件：`.github/workflows/ci.yml`，**5 个 job**：
  - `unit-tests`：`mvn -B test`（无中间件依赖，先绿）
  - `frontend-admin`：`npm ci` + lint + typecheck + build（在 `admin/` 工作目录）
  - `frontend-mini`：`npm ci` + lint + typecheck + `flow`（页面流转静态检查）+ 构建 H5 与微信小程序
    ——两个目标都编：只验 H5 的话，“uni-app 能编小程序”就只是纸面承诺
  - `secret-scan`：① `git ls-files` 中不得出现 `.env`/`logs/`/`*.log`/`target/`/`node_modules/`/`*.pem`/`unpackage/`；② `git grep` 只扫确定性密钥格式（私钥块、`ghp_`、`github_pat_`、`AKIA`、`LTAI`、`xox*`），故意不扫 `password=` 这种文本，避免把 `${MYSQL_PASSWORD}` 占位符误判
  - `integration-tests`：`needs: unit-tests`，MySQL/pgvector/Redis 用 `services`，RocketMQ 用 step 起容器
- **本地与 CI 跑同一批 `@Tag(integration)` 用例**，区别只在环境供给：本地真实例，CI 服务容器；测试代码不分叉
- RocketMQ 不进 `services` 的两个原因：broker 必须 `brokerIP1=127.0.0.1`（否则向 namesrv 注册的是容器内网 IP，runner 宿主进程连不上），且需要 `--net host` 与显式堆参数（镜像默认 8G 堆会弄挂 7G 内存的 hosted runner）
- 配置版本差异（已登记的简化）：CI 用 `pgvector/pgvector:pg16` + `redis:7`，本地是 PG 18.3 + Windows Redis 5.0.14；MySQL 两边均 8.0。差异只影响集成测试环境，版本漂移风险待 CI 跑稳后统一

## 9. 禁止加戏（自我约束，用户 2026-10-09 要求写入）

**病根不是“偶尔没注意”，是一个固定倾向**：被问到“这块怎么防错”时，我会习惯性多造一层防御
（阈值、上限、窗口、开关、新状态、新表）来表现周到；再把规则推到用户没说过的相邻场景上，
然后为那个我自己假设的场景写代码。结果是参数表变长、用例变多、结论看上去很完整，
但**用户要做的是删掉那些他从未要求过的东西**，而这比少写一行贵得多。

### 溯源测试（任一新增物都必须能回答）

> **这个开关/阈值/上限/状态/表/枚举值/前提，能指到用户说过的哪一句话，或已定稿文档的哪一节？**
> 指不到就**不写**：最多写成一条“待定问题”交用户拍板，不得先实现再解释。

典型“禁售品”（我自己造过的，不是假设）：阈值、额度天花板、时间窗口、次数上限、“可选开关”、
“为了完整性再建一张表”、“现实里大多数设备不具备这个能力”这类新前提。

### 例外（只这三种，仍要写清代价）

1. **工程基线要求的**（幂等键、鉴权、审计、租户隔离、条件更新、超时与重试）——这类不叫加戏，
   是《企业标准不得简化》的相反方向；
2. **存储约束代替代码自觉的**（唯一索引、CHECK、`WHERE` 守卫）；
3. **用户原话里的数字**（5 分钟容错、2 小时加收、复审 2 次）。
判定区别很简单：这些限制能不能指向“防一次已发生过的事故”或“用户给过的数字”。
只能指向“万一以后有人乱来”的，就是加戏。

### 防滥用类需求走这条，而不是新增业务参数

权限点（谁能做）→ 幂等（能不能重放）→ 终态保护（做完还能不能做）→ 审计与看板（谁做多了）。
这四件已经在了，所以下次遇到“怕有人乱点”，**不得**再造一个额度/阈值参数。

### 复发记录（留在这里是为了下次别说“这次不一样”）

| 我自造的东西 | 用户原话是什么 | 多付的代价 |
|---|---|---|
| REOPEN 功能（15 分钟窗口、每单 2 次、超窗同远程价） | 只要“误关门后要能再开门” | 单未结束时有临时开柜就够了；整节已删 |
| 欠费“达阈值才拦” | “有欠费就不能用” | 多一个无意义参数，已撤 |
| 人工免除的“单笔/月累计额度” | 无 | 免除金额本就由算法给出，不是人填的；已撤 |
| “大多数柜机只有门磁、拿不到凭据现场采信用户” | 设备必须能回答“有没有东西” | 自己造前提又为它写分支，还漏了锁格；已重写 |
