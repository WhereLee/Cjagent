## 1. 已定决策

| 编号 | 决策 | 内容 | 依据 |
|---|---|---|---|
| D-06 | 账户结构 | 拆成**本金 `balance`** 与**赠送额度 `bonus`** 两个子账户，绝不用一个字段混装；"积分"至多作为**计价单位**（1 积分 = 1 分人民币）出现，不是一种资金 | 行业与司法实践要求两类资金分开记录（来源、有效期、可退性不同）；混装会在退款与对账时炸 |
| D-07 | 扣减顺序 | **先扣将过期的赠送 → 再扣普通赠送 → 最后扣本金** | 顺序是**防套利**设计：决定"充 50 送 20 后立刻退款"能否白嫖；且有"先扣赠送"的真实先例 |
| D-08 | 记账深度 | **双分录账本**：流水只 INSERT 不可改，余额是派生值；退款按资金来源比例还原 | 单流水表能跑通"扣钱"，但回答不了"这 48.1 里本金剩多少、该退多少"——而后者正是这块的存在理由 |
| D-09 | 支付通道 | **推迟到最后**。通道层只留抽象（`PayChannel`），不接也完整；支付宝沙箱属"最后的最后"，用户本就不倾向做 | 账务域不依赖外部通道；资质、公网回调都不是本项目的前提 |
| D-10 | 设备拓扑 | 开发态用**内嵌 Moquette**（纯 Java，本机无 Docker）；演示/联调态 broker 上云，**柜机 A 常驻云服务器、柜机 B 在本地** | 跨网络、真实 RTT、真实可用性域的分布式验证；顺带给运维提供真实对象 |
| D-13 | 营销玩法 | **全砍**：优惠券、满减、拼团、拉新返现、阶梯价、动态加价。仅保留"套餐冻结" | 那是运营深度不是 Java 深度；冻结留下是因为它是"有效期顺延 + 状态机 + 定时解冻"的现成素材 |

合规与措辞：本项目不涉及真实资金。对外表述用**"预付储值账户 + 复式记账 + 可插拔支付通道"**，
不要说"做了个虚拟货币"。真实经营中预付储值受单用途预付卡管理与
**最高法预付式消费司法解释（2025-05-01 施行）第十九条**（`退款 = 实付 − 已兑付打折前金额`）约束，
2026 年换电行业新规亦要求套餐价格、计费规则、押金标准、退租条款**全部公示**——
这些不是包袱，正是上面 D-06/D-07/D-08 的建模依据：**账必须能解释自己**。

## 2. 领域骨架与不变量

**资产侧**：站点 → 柜机 → 仓位 → 电池。**车电分离**：电池是平台资产，骑手购买的是能源服务，
因此每次换电都要产生**流转记录**（哪块电池从哪个仓位进出）。

**用户侧**：骑手 ↔ 租户 ↔ 账户（本金/赠送）↔ 套餐持有 ↔ 换电订单。

三条不变量——**必须写成测试，不能只写在文档里**：

1. 电池库存守恒：`idle + locked + inUse + repairing = 柜内电池总数`
2. 超卖为 0：任意并发下，一块电池不得同时被两个订单持有
3. 账本一致：`Σ(流水) == 账户余额`，且 `balance ≥ 0`、`bonus ≥ 0`

金额一律以**分**为单位存 `long`（与现有 Jackson 约定天然契合：原始 `long` 保持 JSON 数字，
ID 用包装 `Long` 走字符串）；运算用 `BigDecimal`，禁止 `double`；按比例分摊时**最后一笔用减法**兜精度。

## 4. 明确不做（防范围蔓延）

- **营销**：券、满减、拼团、拉新返现、阶梯价、动态加价
- **设备**：温度/电压电流曲线等传感器、固件 OTA、设备影子、告警规则引擎、地理围栏
- **架构**：K8s、微服务拆分、ELK 集中日志、自研 RPC、多支付渠道聚合
- **支付**：真实商户号与微信/支付宝正式接入（D-09，推到最末）
- **架构约束**：骑手端（小程序/H5）**永不直连 MQTT**，只走 HTTP API；否则等于把 broker 暴露给公网用户

## 5. 每刀开工前的重估清单（固定四问）

1. **前一刀实际改了什么？** 本刀原设想依赖的接口、字段、状态位、表结构是否还成立？
   要列出具体类名与文件，不凭记忆。
2. **本刀的可测量验收是什么？** 测试先写还是实现先写？并发类改动必须先有不变量测试。
3. **有没有触碰框架型基线**（异常处理 / 分层 / 幂等 / 租户 / 审计 / 认证）？按企业标准做，
   还是不得不简化？若简化，按红线登记进 `架构约定.md` §7 并在完成时向用户说明。
4. **与 `架构约定.md` 有无冲突？** 有就先改约定，再改代码——约定不能落后于代码。
